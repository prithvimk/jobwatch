# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

jobwatch sends fast job alerts and builds an application kit for one user (who they are, and the screening filter spec, are in the gitignored `CLAUDE.local.md`). The goal is to be among the first ~10 applicants on matching roles. Detection latency and minutes-to-submit are the levers.

## Hard constraints

- Only a Claude Pro subscription. No Anthropic API key, no paid infrastructure.
- Code does all repetitive and fast work: board enumeration, diffing, prefiltering, liveness. Claude only judges *new* roles, which keeps Pro limits from running out.
- The user always clicks the final submit. No auto-applications, no automatic outreach. Outreach goes out only after an explicit yes on recipient and wording, from a spare outreach inbox.
- `private/` (resume, answer bank, ledger, drafts) and `CLAUDE.local.md` are gitignored and must never reach the public repo (github.com/prithvimk/jobwatch). `state/` holds IDs and timestamps only. It is the `state` branch, checked out as a git worktree at `state/` (gitignored on `main`), so `main` holds code alone.
- An unreachable or ambiguous source shows as a visible `unknown`, never a guess. Report a posting date only when the page states it. Otherwise say "first seen <detector run timestamp>".

## Commands

```powershell
uv sync                                                   # install deps (Python 3.13, uv)
uv run pytest -q                                          # all tests
uv run pytest tests/test_board_map.py::test_workday_india_nested_facet -q   # single test
uv run python -m detector.board_map                       # M0: boards_seed.yaml -> boards.yaml
uv run python -m detector.board_map --only Citi --only Visa   # re-probe some boards, print only (no write)
uv run python -m detector.run --dry-run                   # detector pass: prints pushes, writes no state
uv run python -m detector.run                             # live pass: pushes via ntfy, writes state/
uv run python -m detector.sync                            # laptop pass: pull state branch, run (+screen), digest/reminders, status page, commit and push state branch, heartbeat
uv run python -m detector.run --dry-run --screen          # dry pass that also calls Claude on each hit (uses Pro usage)
uv run python -m detector.ledger list                     # unresolved (SHOWN) roles; --all for every mark
uv run python -m detector.ledger applied <ref>            # or skipped / shown (undo); ref = board:id, job id or req id
uv run python -m detector.remind --dry-run                # reminders/weekly lists due now, printed, nothing recorded
uv run python -m detector.status                          # write private/status.html now (sync rewrites it every pass)
uv run python -m detector.sweep JPMC                      # full India board now: counts, candidates, dropped title hits
uv run python -m detector.sweep JPMC --screen             # also screen candidates (cached verdicts reused; --screen-limit 25)
.\scripts\install_task.ps1                                 # register the 5-min Task Scheduler job (log: private/logs/sync.log)
```

To exercise the alert path without waiting for new postings, point `JOBWATCH_STATE_DIR` at a temp dir whose `seen.json` has a board with `baseline_at` set and empty `jobs`. Every current posting then counts as new. Pair this with `--dry-run`.

## Architecture (planned pipeline, built in milestones)

1. **Detector** (code, no LLM, every 10 min): polls each board in `boards.yaml`, diffs requisition IDs against the union of every ID ever seen (`state/`), applies a cheap title/location prefilter, checks that the apply URL is live, pushes title and link via ntfy, and commits only state.
2. **Screener** (Claude, after new IDs appear, at least hourly): fetches the full JD, applies the filter spec below, scores fit, names gaps, and pushes a verdict. Prompts live in `prompts/`.
3. **Application kit** (Claude, same run): the fit verdict with gaps, plus a resume tweak when one is worth making, saved to a doc the alert links to. No drafted screening answers: target boards ask form fields, not essays. `private/answers.md` holds only the facts forms ask that Simplify doesn't fill (notice, CTC, relocation, start date, years). Outreach drafts only on request.
4. **Submit** (user, ~2 min): Simplify autofill plus pasted kit answers.

Also required: an on-demand **sweep** (built: `detector/sweep.py`). Given a company, it enumerates the full India board (all pages), pulls JDs for candidates, reports total counts, and lists filtered-out title hits with the reason.

Build order: M0 board map (done) → M1 detector for easy boards, hosted on the laptop every 5 min with public-repo GitHub Actions as the fallback (built; see `docs/hosting.md`) → M2 adapters, one company at a time, each with a fixture test (built for all 43 boards with a JSON source: Workday for 20 incl. Morgan Stanley, Deutsche Bank and Bank of America (NVIDIA, State Street, Salesforce, Adobe, PayPal and Intel added 2026-11-22; Maersk and FactSet added 2026-11-25; PayPal, Intel, Maersk and FactSet are city-level like Cisco), Oracle for JPMC and Goldman Sachs, Greenhouse for Databricks, Rubrik, HackerRank, Zscaler, Coinbase, Twilio and Cloudflare (2026-11-25), Lever for Meesho and Netomi, Ashby for Sarvam, SmartRecruiters for Swiggy and ServiceNow, Amazon, Eightfold for Microsoft, Eightfold AI and HSBC (2026-11-25, v2 API), Jibe for MSCI and HERE, Atlassian, gr8 People for Teradata and Radancy for Moody's (both added 2026-11-22); the 2 `custom-scrape` boards (Google, Sony Research India) and SISC are not watched) → M3 screener (built; inputs `private/resume.md`, `private/answers.md`, the filter spec in `CLAUDE.local.md`) → M4 ledger, reminders, digests (built) → M5 optional Claude-in-Chrome prefill that stops before submit.

## Board map (`detector/board_map.py`, `boards_seed.yaml` → `boards.yaml`)

- `boards_seed.yaml` is hand-maintained. `hints` are explicit ATS locators found by reading each careers page and a sample job page, and they are tried before HTML fingerprinting. Many corporate careers sites (Phenom, Radancy/TalentBrew, Jibe, Eightfold) are front ends. The apply button goes to the real ATS, so locate the backend from a **job detail page**, not the landing page.
- `effort` tiers: `easy` (Greenhouse/Lever/Ashby/SmartRecruiters public JSON), `adapter` (Workday CXS / Oracle HCM REST: one generic adapter, per-company config), `custom-json` (stable undocumented JSON: Amazon `search.json`, Eightfold `/api/pcsx/search`, Jibe `/api/jobs`, Atlassian listings, Deutsche Bank BeeSite, gr8 People GraphQL, Radancy `search-jobs/results`), `custom-scrape` (HTML only).
- **Workday throttles per source IP across all tenants.** A burst of a few dozen requests caused 429s on every tenant for several minutes. All Workday calls are serialized under `WORKDAY_LOCK` and paced, and a 429 is recorded as `unconfirmed`, never as `unknown` ATS. Plan the detector cadence around this limit.
- Goldman Sachs: higher.gs.com is a front end (GraphQL at `api-higher.gs.com`) whose apply links go to Oracle (`hdpc.fa.us2.oraclecloud.com`, site `LateralHiring`), so it is tracked on Oracle. The front end also lists roles Oracle has closed (15 of 132 India roles, 2026-11-22). Eightfold AI posts on its own Eightfold site (`app.eightfold.ai`, domain `eightfold.ai`) and, as an AI-native company, gets Sarvam's engineering/scientist `extra_include` in `detector/config.yaml`.
- Coverage notes: Sony means Sony Research India (openings are LinkedIn links on its WordPress careers page) plus Sony India Software Centre (no public board found, kept as `unknown`). Neither posts on Sony's global Workday. Prodigal and Zwayam were dropped and Bank of America added. Front ends whose apply button goes to Workday are tracked on Workday instead: Morgan Stanley (Eightfold → `ms.wd5 External`), Deutsche Bank (BeeSite → `db.wd3 DBWebsite`, 311 India vs 241 in BeeSite) and Bank of America (`ghr.wd1 lateral-ba_continuum`, a site holding only its India postings; its `jobssearchservlet` also lists them, with years of experience).
- India counts: Workday reads the country facet (`india_facet` gives the `appliedFacets` key/id to filter on), Oracle uses the `LOCATIONS` facet, and others filter location strings or use the API's country param.

## Detector (`detector/run.py`)

- Boards are read from `boards.yaml`. A board runs if its `ats` has a fetcher in `detector/sources.py:FETCHERS` (greenhouse, lever, ashby, smartrecruiters, workday, oracle, amazon, eightfold, jibe, atlassian, gr8people, radancy). Custom-JSON boards (`ats: custom`) are keyed by their `platform` (`run.kind`). A fetcher is called as `fetcher(client, board_entry, skip=, location_ok=, full=)` and returns `Job`s; the JSON boards ignore the context, incremental ones use it to stop paging.
- `posted_at` is set only from a date the ATS states (Greenhouse `first_published`, Ashby `publishedAt`, SmartRecruiters `releasedDate`, Workday detail `startDate`, a date without a time; Oracle `PostedDate`, then the detail's exact `ExternalPostedStartDate`). Oracle also states a closing date (`ExternalPostedEndDate`); alerts show it, and JPMC postings often close within 1-2 weeks. Lever's `createdAt` is deliberately not used. Otherwise alerts say "first seen <run time>".
- Flow per pass: fetch → new IDs = not in `state/seen.json` (IDs are never deleted, so a repost under the same ID is never new) → prefilter (`detector/config.yaml`, inclusive by design; it returns a reason for every decision) → liveness (ATS detail API, JD page, apply page; closed-page redirects and closed text fail it) → ntfy push → save state. A board with no state is **baselined** silently on its first pass.
- JD keyword pass (`jd_check` in `config.yaml`, `run.jd_pass`): a new posting whose title matches no include pattern but no exclude pattern either, in an allowed location ("Software Engineer II", "Research Analyst"), gets status `jdcheck`, and its JD is read (detail hook first where the ATS has one, then `jd.get`). Titles matching `jd_check.title_exclude` (manager, architect, auditor, designer, support…: functions the spec never takes) skip it. Plain code, no Claude: distinct weighted signals (LLM, RAG, PyTorch, fine-tuning, machine learning…; a bare "AI" does not count, and "agents" counts less because Salesforce's Agentforce is a product name) are summed from the first qualifications heading on, because Amazon's team blurbs mention GenAI and agents on unrelated roles. At `threshold` the posting goes on as `pending` with `via: jd` and is screened like any other hit; below it, `filtered` with its `jd_score`. At most `max_per_pass` (40) are read per pass; the rest stay `jdcheck` for the next. An unreadable JD is retried `max_liveness_tries` times, then recorded as `jd_score: unknown`. Calibrated 2026-11-25 on 1,005 title misses sampled from 43 boards (up to 80 per board, newest first): 63 (6.3%) pass at threshold 5, about 15 extra screenings a day at ~250 title misses a day. Examples that pass: JPMC "Software Engineer II" (GenAI, RAG, agents, LangChain), Bank of America "Software Engineer III", HackerRank "Senior Backend Engineer", Microsoft "Software Engineer II" (LLM, agents). `tests/test_detector.py::test_applied_roles_pass_the_title_filter` checks every APPLIED title in the private ledger against the title filter and the JD pass (skipped without `private/`).
- A posting that fails liveness stays `pending` and is retried for `max_liveness_tries` passes, then becomes `dead`. A failed push stays pending too. SmartRecruiters' apply entry page (`/oneclick-ui/`) returns 403 to every non-browser client, so a redirect into it counts as resolved and is labeled that way.
- Workday (`detector/workday.py`): every call goes through system `curl`, paced 1 s apart, because Python TLS clients get 429. Lists are newest first, 20 per page, so a normal pass stops at the first page with nothing unseen or pending; each board gets a full sweep every 12 passes, rotated so only one board sweeps per pass. Country-facet tenants use `india_facet`; city-level tenants (Cisco, Mastercard, BlackRock, Barclays, PayPal, Intel, Maersk, FactSet) filter on the allowed-city location values read from the first response. List rows saying "N Locations" have no locations until the detail API fills them in, and the prefilter is re-run then. The JD page is a JS shell that returns 200 even when closed, so the detail API (404 once closed, `canApply`) decides liveness.
- Oracle Recruiting Cloud (`detector/oracle.py`, locator = host + siteNumber): India via the `LOCATIONS` facet id, pages of 200 sorted newest first, so a full fetch every pass is 1-2 calls. The detail API returns no items for a closed posting and the job page is a JS shell, so the detail API decides liveness. ATSs needing a detail lookup register `(enrich, live)` in `sources.detail_hooks`.
- Amazon (`sources.amazon`, amazon.jobs `search.json`): `country=IND`, 100 per page, `sort=recent` (newest first only roughly within a day), incremental like Workday. `posted_date` is stated ("November 20, 2026"). A closed job's page returns 404. The apply link sends every job through an SSO redirect chain that drops non-browser clients, so for hosts in `run.SIGNIN_APPLY_HOSTS` only the first hop is checked.
- Eightfold (`detector/eightfold.py`, Microsoft): a fresh client's first call gets 429 and sets `_vs*` cookies, and bursts get 429, so calls are 3 s apart with one retry. Search is `location=India&sort_by=timestamp`, 10 per page, incremental; `postedTs` is the stated time. `position_details` 404s once closed and the job page is a JS shell, so it decides liveness. Morgan Stanley's Eightfold site is only a front end: its apply button goes to `ms.wd5.myworkdayjobs.com/External`, so it is tracked with the Workday adapter.
- Eightfold v2 (HSBC, `portal.careers.hsbc.com`): older tenants answer "PCSX is not enabled", so the endpoint is `/api/apply/v2/jobs` (same paging, 10 per page, but "hot" postings are pinned to the first page, so an incremental pass reads at least two). No posting date is stated (`t_create` is Eightfold's record time, not used). `/api/apply/v2/jobs/<id>` (404 once closed) gives the JD and the SuccessFactors apply link; SuccessFactors answers 200 with a sign-in page for any requisition, so liveness requires the req id in the apply page's `<title>` (which sits ~300 KB into the page).
- Jibe (`sources.jibe`, MSCI and HERE): `<site>/api/jobs?location=India`, read in full every pass (tens of postings; `sortBy` returns 503). `posted_date` and, when present, `posting_expiry_date` are stated. A closed job's page returns 404 and the apply link is the iCIMS login page, so the generic liveness check works.
- Greenhouse: some boards put only the work style in `location` (Cloudflare: "Hybrid") and the cities in a custom field ("Job Posting Location"), so any metadata field whose name contains "location" is added to the posting's locations.
- Atlassian (`sources.atlassian`): one call lists every posting worldwide (~230); India is kept by location text. No posting date is stated, so alerts say "first seen". A closed iCIMS job page returns 410.
- gr8 People (`detector/gr8people.py`, Teradata): a Next.js site over GraphQL at `/graphql`, which answers UNAUTHENTICATED until `/jobs` has set the `token` cookie, so each pass loads `/jobs` first. `searchJobPostings(first, start)` returns at most 100 per call, newest first, worldwide (~200) with no country filter, so every pass reads all pages (2-3 calls) and keeps postings with an Indian place. `postedOn` is stated. The job page (`/jobs/<key>/<slug>`, a wrong slug redirects) embeds the posting in `__NEXT_DATA__` with `status` and the JD, so it is the detail check; a posting that isn't open returns 404.
- Radancy (`detector/radancy.py`, Moody's): the site's own `search-jobs/results` AJAX call returns JSON wrapping an HTML list; the India country facet (type 2, id 1269750, the GeoNames id) gives Moody's India (~50) in one call, read in full every pass. List rows have no date. The job page's JSON-LD states `datePosted` (a date), `identifier` (the SuccessFactors Job ID, used as `req`), every location and the JD; a closed job page returns 404. Apply (`data-apply-url`) goes to SuccessFactors `jobreqcareer`, which answers 200 for closed requisitions too, so liveness requires the Job ID in that page's title.
- `state/health.json` changes only when a board starts or stops failing, so healthy passes commit nothing. After `board_fail_alert_after` failures in a row, it pushes an "unreachable" alert.
- Two runners share `state/` through git: the laptop (`detector/sync.py`) and Actions. Both commit and push only the `state` branch (root: `seen.json`, `health.json`, a `.gitattributes`); the laptop never pulls or pushes `main`, so code reaches GitHub only when the user pushes. `sync.py` creates the `state/` worktree if missing and skips the pass (never runs on empty state) if `state/` is something else. The JSON files merge by meaning via `detector/merge.py`, a git merge driver run as a plain script (stdlib only) because git calls it from the worktree, so IDs are never lost when both commit. Actions skips while the repo variable `JOBWATCH_LOCAL_AT` (the laptop's heartbeat) is under 15 min old.
- The ntfy topic is a secret: anyone who knows it can read the alerts. Locally it is read from `private/ntfy.env`; in Actions it comes from the `NTFY_TOPIC` secret. With no topic set, pushes print instead of sending and postings stay pending.

## Screener (`detector/screen.py`, `prompts/screen.md`)

- Runs only on the laptop: `sync.py` turns it on when `screen.available()` (the `claude` CLI at `~/.local/bin`, `private/resume.md`, `private/answers.md`, and a `## Filter spec` section in `CLAUDE.local.md`). Actions never screens; its alerts say "Screening pending."
- One `claude -p --output-format json --max-turns 1 --model haiku` call per live hit (Haiku spares Pro usage; `JOBWATCH_SCREEN_MODEL=sonnet` overrides; about 20 s each), run in a temp dir outside the repo (so no CLAUDE.md is loaded) with tools disallowed. The prompt carries the spec, resume, facts and the full JD from `detector/jd.py` (ATS API text where available, else the JD page's text, and the source is named).
- The verdict comes only from the spec's exclusion rules; seniority uses the experience floor (≤3 or not stated IN, >3 to 5 STRETCH, ≥6 OUT). Degree and skill bars lower `fit` through the checklist, never OUT on their own. Checked on 12 live postings, 2026-11-21, and on JPMC's 30 sweep candidates, 2026-11-22: Haiku gave the same 30 verdicts as Sonnet (fit within one point) but took about 21 s per call against Sonnet's 9 s through the CLI. Haiku is the default since 2026-11-22 to spare Pro usage; screening adds about 10 s more to an alert than Sonnet would. The track rule accepts data-science roles where ML is only preferred (pure BI and data engineering stay out); after that change, 14 track-excluded JPMC roles were re-screened and only the data-science one flipped, consistently across two runs.
- Fit is computed in code, never asked of Claude (`screen.score`), so the same marks always give the same score. Claude fills a requirements checklist: `required` and `preferred`, one item per posting bullet (never split or merged), each `status` shown/partial/missing against the resume and facts, `hard` for bars no skill substitutes (degree-only, publications, patents, a skill-specific duration, a required certification), and `evidence`. The overall years ask and soft skills are left out (the verdict already uses years). Coverage = (shown + ½ partial) / required items; fit 5 at ≥0.9, 4 at ≥0.75, 3 at ≥0.55, 2 at ≥0.35, else 1; a missing hard bar caps fit at 2 and a partly shown one at 3; OUT is 1; no readable requirements gives fit `?` (shown as unknown with `checklist_note` saying how many items were unreadable, still alerted). The parser accepts renamed fields (`requirement` for `req`, "met" for shown) because Haiku sometimes renames them. Gaps come from the same checklist: unmet hard bars, then missing, then `partial: …`. `screen.rank` is the one sort key for alerts, the status page, reminders and sweeps: fit, then IN before STRETCH at equal fit, then coverage, then preferred coverage. Alerts and kits say "fit 3/5 (5 of 8 required, 1 partial)", and the kit carries the checklist with evidence. Verdicts cached before 2026-11-25 have no checklist and keep their old holistic fit.
- Reply: one JSON object (`verdict` IN/STRETCH/OUT, `required`, `preferred`, `location`, `experience_asked`, `one_line`, `out_reason`, `out_short` (OUT only, at most 60 characters, for the digest), `resume_tweak`, `skills`). The cached verdict also gets `screened_at` and `title`. Verdicts are cached in `private/verdicts.json` by `board:id`, so a retried push never re-screens.
- IN/STRETCH: one push per role (title prefixed with the verdict, IN at priority 4), best fit first, and a kit in `private/kits/`. OUT: no push, state status `screened`, queued in `private/digest.json` and sent as one digest at the first laptop pass after 20:00 IST: company · title, then `out_short` (else the full reason clipped to 80 characters), a blank line between roles, capped at 3,800 bytes with "…and N more" so ntfy never turns it into a file attachment (over 4,096 bytes). Any screening failure (not logged in, timeout, bad reply) sends the plain alert with "Screening unavailable: <reason>"; a role is never dropped.
- The task's time limit is 20 min (`scripts/install_task.ps1`) because a pass with several hits makes several Claude calls.

## Sweep (`detector/sweep.py`)

- Covers what the detector cannot: postings already open when a board was baselined never alert. A sweep fetches with `full=True`, no skip set, and an India-only location check (North India is fetched so it can be counted and reported), so Workday city-level tenants return every India city.
- Report: postings fetched (and how many are outside India), India total (and how many state no location), candidates, title hits dropped by the prefilter with the reason (`Prefilter.title_hit`: the title matched an include pattern), and the count of other India titles. Candidates get the detail hook where the ATS has one (a failure lists the posting as not confirmed open; detail locations can move it to the dropped list), the JD via `detector/jd.py`, and a history label from `state/seen.json` and the ledger (baseline, alerted, APPLIED/SKIPPED, repost of a resolved requisition, or new).
- Without `--screen`, each candidate shows the first phrase in its JD stating a number of years, quoted verbatim and not judged. With `--screen`, candidates without a cached verdict are screened (at most `--screen-limit`, default 25, Pro usage; the rest are named as not screened); APPLIED/SKIPPED roles and reposts of them are never screened. IN/STRETCH get a kit.
- Pushes nothing and writes no `state/`. The report prints and is saved to `private/sweeps/<date>-<company>.md`. A board without a fetcher, or a name not in `boards.yaml`, prints as `unknown`. Names match exactly (any case), else by substring.

## Filter spec

The screener's filter spec (location, seniority band, track, hard bars, excluded employers) is personal and lives in `CLAUDE.local.md`. The detector's cheap title/location prefilter is `detector/config.yaml`.

## Alerts and ledger

- Before any alert, the live JD page must load and the apply link must resolve to the entry page (sign-in/autofill). Check both at alert time.
- One message per role: company, title, location, in-band/STRETCH, a one-line fit with gaps, a direct link. Order by fit, then newest.
- Ledger keyed by exact requisition ID with states SHOWN / APPLIED / SKIPPED. APPLIED and SKIPPED are never re-recommended, even if reposted. Check history before calling anything "new".
- Built (`detector/ledger.py`, `private/ledger.json`): an entry per alerted posting keyed `board:id` (as in `verdicts.json`), with `req`, title, links, stated closing date and verdict. A successful push records SHOWN. A new posting with the same board and `req` as an APPLIED/SKIPPED entry is not screened or pushed (state status `repost`); a repost of a SHOWN role is alerted with a "Repost" line. Matching uses the exact requisition id only, never titles.
- Marking: each alert's buttons are Apply (view), Applied and Skip (ntfy `http` actions POSTing `"applied <board:id>"` to the reply topic, `NTFY_REPLY_TOPIC`, default `<NTFY_TOPIC>-reply`; tapping the notification opens the JD). `sync.py` polls the reply topic before each pass and keeps the last message id in the ledger. ntfy.sh keeps messages 12 h, so taps made while the laptop is off longer are lost: mark them with the CLI. The ledger is laptop-only: Actions has no `private/`, so it neither suppresses reposts nor records SHOWN; its alerts still carry the buttons.
- Follow-through: closing-date reminder ~2 days before close if there's no reaction, a weekly list of unresolved roles, one follow-up after 5 quiet days, and a Sunday digest of the skills the week's JDs asked for.
- Built (`detector/remind.py`, run by `sync.py` after each pass, laptop only): a SHOWN role with a stated `closes_at` gets one reminder when 2 days or less remain, after a still-open check (the stored detail-API `check_url`, else the JD page). Closed early: no push, `closed_at` recorded. Unconfirmed: pushed, saying so. An APPLIED role gets one nudge 5 days after `marked_at` (status check; a follow-up draft only on request). Sunday after 20:00 IST: the SHOWN roles from the last 30 days that haven't closed, and the skills the week's screened JDs asked for (the screener's `skills` field, counted, marked "not on resume" when `resume.md` doesn't mention them; verdicts from before 2026-11-22 have no `skills`). Pushes wait for 09:00-22:00 IST unless a role closes within 12 h. Each send is recorded in the ledger (`reminded_at`, `followed_up_at`, `sent`).
- Status page (`detector/status.py`, laptop only): `sync.py` rewrites `private/status.html` at the end of every pass, so the ledger and pipeline can be checked in a browser instead of with the CLI. It shows the SHOWN roles (best fit first, with verdict, gaps, stated closing date, kit and links), APPLIED/SKIPPED from the last 30 days, the runner (when the page was written, with a warning after 15 min with no pass; the last state commit and its runner; problem lines logged by this pass), the last 7 days' new postings by status, tonight's OUT digest queue, and per-board health and counts (failing boards first, unwatched boards as `unknown`). It is a static file with no server: its Applied/Skip/Undo buttons POST the same text as the phone buttons to the reply topic (ntfy.sh allows any origin), so the next pass records them. The page holds the reply topic and any `NTFY_TOKEN`, so it stays in `private/`.
